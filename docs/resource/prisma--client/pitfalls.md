# Known Pitfalls & Gotchas

| Scenario | Risk or surprising behavior | Required handling | Evidence |
|---|---|---|---|
| Constructing a client per request/module evaluation | Every PrismaClient owns a query engine and connection pool; repeated instantiation can exhaust database connections. | Reuse one client per process; in Next.js development cache it on `globalThis` to survive hot reload. | [Web] [Instantiating Prisma Client](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/instantiate-prisma-client.md) |
| Serverless scale-out | Each concurrent function/container may own its own pool; global singleton only deduplicates within one process, not across instances. | Set realistic connection limits, use an external pooler where needed, and account for concurrency across all instances. | [Web] [Connection pool](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/connection-pool.md) |
| Calling `$disconnect()` after every web request | Tears down reusable connections; next request incurs reconnect overhead and harms throughput. | Keep the client alive in long-running web processes; disconnect only finite scripts or process shutdown. | [Web] [Connection management](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/connection-management.md) |
| Assuming client connection happens at construction | Prisma connects lazily on first query; initialization/credential errors can surface on first actual query. | Use `$connect()` only when eager startup is intentional; handle initialization errors at application startup/request boundaries. | [Web] [Connection management](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/connection-management.md), [errors](https://www.prisma.io/docs/orm/v6/reference/error-reference.md) |
| Pool saturation (`P2024`) | Query waits for a free pool connection then times out; retries without capacity control can worsen overload. | Investigate slow/long queries and pool limits, cap concurrent workload, and use an appropriate pooler; don't blanket-retry. | [Web] [Connection pool](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/connection-pool.md), [P2024](https://www.prisma.io/docs/orm/v6/reference/error-reference.md#p2024) |
| Long-running interactive transaction | Holds transaction/connection; slow network calls can cause contention, timeouts, or deadlocks. | Keep transaction callback short; do not perform remote calls or long computation inside it. Set timeout/isolation only to fit explicit workload needs. | [Web] [Transactions](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions.md#interactive-transactions) |
| Assuming `$transaction([])` accepts awaited results | An `await` executes query before batching; transaction API needs PrismaPromise instances. | Pass delegate calls directly in the array; for dependent control flow use interactive transaction. | [Web] [Sequential transactions](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions.md#sequential-prisma-client-operations) |
| Combining `select` and `include` at top query level | Prisma rejects their simultaneous top-level use. | Use `select` with nested relation `select` to shape both scalar and related output. | [Web] [Select/include](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#select) |
| Large unbounded `findMany()` | Loads and serializes potentially huge result sets, increasing database and process memory pressure. | Bound `take`, select only needed fields, filter, and paginate; use cursor pagination for large feeds. | [Web] [findMany](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#findmany), [pagination](https://www.prisma.io/docs/orm/v6/prisma-client/queries/pagination.md) |
| `deleteMany()` / `updateMany()` without `where` | Applies to all rows. | Require an explicit predicate in application-level destructive operations; use count checks/transaction where warranted. | [Web] [Client API](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#deletemany) |
| Assuming top-level `createMany` supports nested relations | It does not support nested relation creation/connection. | Use nested `create` / nested `createMany` within a parent operation or separate explicit transactional operations. | [Web] [createMany](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#createmany) |
| Upsert race under concurrent requests | Depending on connector/query shape, concurrent upserts can surface unique conflicts instead of transparently succeeding. | Enforce DB uniqueness; handle `P2002` as a narrowly identified conflict and retry only if operation is idempotent and race handling is designed. | [Web] [upsert](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#upsert), [P2002](https://www.prisma.io/docs/orm/v6/reference/error-reference.md#p2002) |
| Catching all Prisma errors as “not found” | Hides validation, network, authentication, pool, and engine faults. | Handle `PrismaClientKnownRequestError` by code; preserve/rethrow other errors. `findUnique()` returns null, whereas `findUniqueOrThrow()` throws on no row. | [Web] [Error reference](https://www.prisma.io/docs/orm/v6/reference/error-reference.md), [findUnique](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#findunique) |
| Schema changes without client regeneration | Generated delegates/types remain stale or unavailable; custom output import will fail or disagree with schema. | Run `prisma generate` after schema changes and deploy the generated client compatible with the Prisma CLI/runtime version. | [Web] [Generating Prisma Client](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/generating-prisma-client); `[Code]` `prisma/schema.prisma`, `package.json` postinstall |
| Logging query events in production | SQL and parameter values may contain sensitive data; verbose logging adds operational noise. | Keep production log levels intentional; redact/sanitize event output and never log secrets or credentials. | [Web] [Client reference logging](https://www.prisma.io/docs/orm/v6/reference/prisma-client-reference.md#log) |

# Known Pitfalls & Gotchas

| Scenario | Risk or surprising behavior | Required handling | Evidence |
|---|---|---|---|
| Calling `.parse()` for untrusted input without catching | Invalid values throw `ZodError`, potentially becoming an unhandled request failure. | Use `safeParse()` for expected user errors, or catch and map `ZodError` to the intended response. | [Web] [Parsing](https://v3.zod.dev/?id=parse), [safeParse](https://v3.zod.dev/?id=safeparse) |
| Assuming `safeParse` catches exceptions from arbitrary user callbacks | It returns a validation result for Zod issues; custom refinement/transform callbacks can themselves throw. | Make callbacks total for expected input and handle operational exceptions separately. | [Web] [Refinements](https://v3.zod.dev/?id=refine), [Transforms](https://v3.zod.dev/?id=transform) |
| Using async `.refine()`/`.transform()` with sync parse | Sync parse APIs cannot execute async schema effects. | Use and await `parseAsync()` / `safeParseAsync()` whenever async effects are present. | [Web] [Async parsing](https://v3.zod.dev/?id=parseasync) |
| Assuming objects reject unknown keys | `z.object()` strips unknown keys by default, it does not reject them. | Choose explicitly: `.strict()` to reject, `.passthrough()` to preserve, `.strip()` to strip; do not rely on defaults for security semantics. | [Web] [Objects](https://v3.zod.dev/?id=objects) |
| Using `z.coerce.boolean()` for textual flags | JavaScript `Boolean("false")` is `true`, because non-empty strings are truthy. | Validate explicit textual values with `z.enum(["true", "false"]).transform(...)`; do not treat generic coercion as semantic parsing. | [Web] [Coercion](https://v3.zod.dev/?id=coercion-for-primitives) |
| Using `z.coerce.number()` on empty form fields | `Number("")` and whitespace-only strings become `0`; malformed numeric strings become `NaN`. | Preprocess blanks to `undefined`/a deliberate default, then validate finite/range constraints. | [Web] [Coercion](https://v3.zod.dev/?id=coercion-for-primitives) |
| Assuming coercion accepts only the intended source type | Coercion uses JavaScript constructors and can accept surprising inputs such as booleans or `null` for numbers. | Restrict raw input type in `preprocess` or validate source strings before conversion. | [Web] [Coercion](https://v3.zod.dev/?id=coercion-for-primitives) |
| Assuming parse returns the same object reference | Successful `.parse()` returns a strongly typed deep clone, incurring allocation and changing identity. | Use parsed output as canonical validated data; avoid relying on reference identity or mutating the original as if it were the returned value. | [Web] exact-version [README](https://github.com/colinhacks/zod/blob/v3.25.76/packages/zod/README.md) |
| Composing object schemas with intersection unnecessarily | Intersections can yield less ergonomic types and object methods are not available on the resulting intersection schema. | Use `.extend()` or `.merge()` for object composition where appropriate. | [Web] [Intersections](https://v3.zod.dev/?id=intersections) |
| Treating `z.infer` as the accepted input type after transforms | `z.infer` describes output, which may not accept raw input. | Use `z.input<typeof Schema>` for pre-transform inputs and `z.output`/`z.infer` for parsed results. | [Web] [Basic usage](https://v3.zod.dev/?id=basic-usage) |
| Passing detailed issues to clients | Validation messages/paths may disclose internal schema details; raw submitted values should not be logged. | Return only intended fields/messages and avoid logging secrets or full invalid payloads. | [Web] [Error handling](https://v3.zod.dev/?id=error-handling) |
| Expecting client-side checks to enforce security | Browser validation is bypassable. | Re-parse at server boundaries and independently perform authorization and business rules. | [Web] [Basic usage](https://v3.zod.dev/?id=basic-usage); operational security requirement |
